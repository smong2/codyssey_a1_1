## 1. 커밋 메시지 규칙 및 단위 설명 (Commit Convention)

안정적인 버전 관리와 변경 이력 추적을 위해 **기능 단위(Feature-based) 커밋** 원칙을 수립하고, 다음과 같은 커밋 메시지 규칙을 적용하여 작업 의도를 명확히 했습니다[cite: 7].

### 커밋 메시지 규칙

| 태그         | 설명             | 예시 커밋 메시지                                    |
| :----------- | :--------------- | :-------------------------------------------------- |
| **feat - code**     | 새로운 기능 추가 | `code or feat: 프롬프트 추가, 저장, 불러오기 기능 업데이트` |
| **fix - code**      | 버그 수정        | `code or fix: 한글 출력 시 터미널 정렬 깨짐 현상 수정`      |
| **document**     | 문서 추가/수정   | `document: git ignore 설정 테스트 및 리드미 업데이트`   |
| **refactor** | 코드 리팩토링    | `refactor: 기능별 분리 (서브메뉴 핸들러 도입)`      |
| **initial**     | 프로젝트 초기화  | `init: 기본 설정 작업 및 파일 경로 세팅`            |

**기능 단위 커밋의 장점:** 각 커밋이 '프롬프트 추가 기능 완성', '마크다운 내보내기 기능 완성'과 같이 독립적인 모듈 단위로 구성되어 있어, 특정 기능에 문제가 발생했을 때 롤백(Rollback)하거나 원인을 파악하기 용이합니다[cite: 7].

## 2. 자료구조 선택의 논리 (List vs. Dictionary)

본 프로그램에서 프롬프트 데이터를 저장하고 관리하기 위해 **'딕셔너리(Dictionary)를 요소로 갖는 리스트(List)'** 구조를 채택했습니다[cite: 7].

### 자료구조 비교 및 선택 이유

| 자료구조       | 장점                                                                                                                                         | 단점                                                                | 본 프로젝트 적용 논리                                                                                                                                                    |
| :------------- | :------------------------------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------ | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **List**       | - 순서(Index)가 유지됨<br>- 데이터를 순차적으로 나열하고 반복문(for)을 돌리기에 최적화됨<br>- `.append()`, `.remove()` 등 추가/삭제가 직관적 | 특정 키(Key) 값으로 즉시 검색하기 어려움                            | 프롬프트 **목록을 순서대로 출력**하고, 번호 기반으로 상세 조회를 수행해야 하므로 **전체 데이터 컨테이너로 리스트가 가장 적합함.**                                        |
| **Dictionary** | - 키(Key)를 통한 직관적인 데이터 접근 (`prompt['title']`)<br>- 데이터의 속성(스키마)을 명확히 정의 가능                                      | 순서가 보장되지 않음 (Python 버전에 따라 다르나 본질적 목적이 아님) | 개별 프롬프트는 '제목, 내용, 카테고리, 조회수, 즐겨찾기 여부' 등 다양한 속성을 가지므로, **데이터의 명확한 구조화(가독성)를 위해 개별 데이터 단위로 딕셔너리를 사용함.** |

> **결론:** 전체 프롬프트의 순차적 관리 및 출력을 위해 **리스트**를 바깥 구조로 사용하고, 각 프롬프트의 상세 속성을 이름(Key)으로 직관적으로 관리하기 위해 내부에 **딕셔너리**를 결합하여 두 자료구조의 장점을 모두 취했습니다[cite: 7].

## 3. Git 브랜치 전략 및 병합 과정

하나의 메인 브랜치에서만 작업할 경우, 실험적인 기능 개발 중 발생하는 오류가 전체 프로그램의 동작을 멈추게 할 수 있습니다[cite: 7]. 이를 방지하기 위해 **기능 분리형 브랜치 전략**을 사용했습니다[cite: 7].

### 브랜치 분리 및 병합 과정

1. **분리 목적:** 새로운 기능(프롬프트 목록 조회 UI 개발 등)을 개발할 때 안정적인 `main` 코드베이스를 보호하기 위해 브랜치를 분리했습니다[cite: 7].
2. **분리 실행:** `git checkout -b module/list_prompts` (기능별 브랜치 네이밍 적용)[cite: 7]
3. **병합 시점:** 분리된 브랜치에서 기능 구현과 단위 테스트를 완료하고, 기존 기능들과 충돌 없이 정상 동작함이 검증된 직후 `main` 브랜치로 `merge`를 수행했습니다[cite: 7].

## 4. 병합 충돌(Merge Conflict) 해결 절차

브랜치 병합 시 동일한 파일의 같은 라인이 수정된 경우 충돌이 발생할 수 있습니다[cite: 7]. 본 프로젝트에서는 협업을 가정하여 다음과 같은 충돌 해결 정책을 수립했습니다[cite: 7].

1. **충돌 인지:** `git merge <브랜치명>` 실행 후 `CONFLICT` 메시지 발생 시, `git status`를 통해 충돌난 파일 목록 확인[cite: 7].
2. **수동 병합:** 충돌난 파일을 편집기로 열어 `<<<<<<< HEAD`, `=======`, `>>>>>>>` 마커를 확인[cite: 7].
3. **코드 수정:** 현재 브랜치의 코드와 병합할 브랜치의 코드를 논리적으로 비교하여, 두 변경 사항을 모두 수용하거나 하나를 선택하여 코드를 정리하고 마커를 삭제[cite: 7].
4. **해결 완료:** `git add <수정된 파일>` 실행 후 `git commit`을 통해 병합 완료 및 충돌 해결 내용을 커밋 메시지에 명시[cite: 7].

## 5. 카테고리 관리 및 수정 정책

프로그램 내에서 카테고리는 동적으로 관리됩니다[cite: 7].

- **추가/할당:** 프롬프트 신규 등록 시 기존 카테고리 목록을 보여주고, 사용자가 직접 번호를 선택하거나 0번을 눌러 새로운 카테고리를 유연하게 생성/할당할 수 있도록 구현했습니다[cite: 7].
- **카테고리 수정 정책:** 현재 프로그램은 개별 프롬프트의 카테고리 일괄 변경 기능을 제한하고 있습니다[cite: 7]. 이는 카테고리의 무결성을 유지하고 오타로 인한 파편화를 방지하기 위함입니다[cite: 7]. (추후 버전에서는 카테고리 관리 전용 메뉴를 통해 카테고리명 자체를 수정하면 연관된 모든 프롬프트의 카테고리가 일괄 업데이트되는 기능을 검토할 예정입니다[cite: 7].)
